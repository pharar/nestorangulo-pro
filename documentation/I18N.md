# Internationalisation (en / es)

The site is English-first with a Spanish version. English keeps its URLs (`/about/`);
Spanish lives under `/es/` with the same path segments (`/es/about/`,
`/es/speaking/<id>/`, `/es/writing/<id>/`). There is no automatic redirect by browser
language: the visitor chooses with the language link in the header.

## How locales and routes work

- `astro.config.mjs` declares `i18n` (`defaultLocale: 'en'`, `locales: ['en', 'es']`,
  `prefixDefaultLocale: false`) and the sitemap's `i18n` option (`en` -> `en`, `es` -> `es-ES`).
  `src/i18n/config.ts` mirrors it for code (`LANGS`, `Lang`, `DEFAULT_LANG`, `OG_LOCALES`).
- The language of a request comes from the URL: `langFromUrl(Astro.url)`.
  `BaseLayout` does this itself, so a page only passes `lang` when its _content_ language
  differs from the route (a Spanish-language talk on the English route).
- `src/i18n/utils.ts`: `langFromUrl`, `stripLang`, `localizePath(path, lang)`,
  `alternatePath(path)`, `switchTarget(pathname, hasAlternate)`, `formatDate(date, lang)`.
  Always build internal links with `localizePath('/about/', lang)`.
- `BaseLayout` takes `hasAlternate` (default `true`). While true it emits
  `hreflang` `en` / `es` / `x-default` (English), `og:locale:alternate`, and the language
  link points at the equivalent page. Pass `hasAlternate={false}` for a page that exists in
  one language only (an essay without a translation, the 404): no hreflang, and the
  language link goes to the other language's section index (`/writing/`, `/speaking/`) or home.
- Canonical, `<html lang>`, `og:locale` and JSON-LD `inLanguage` are per page; the
  breadcrumb root is "Home" / "Inicio".
- The header language link (`LanguageSwitch.astro`) is a plain `<a>` showing the _target_
  code ("ES" on English pages, "EN" on Spanish ones), with `hreflang`, `lang` on the text
  and an aria-label in the target language. No JavaScript, no flags.

## The page pattern: view + thin wrappers

1. Put the markup in `src/views/<Page>.astro`, taking `lang: Lang`. All copy comes from a
   dictionary; links go through `localizePath`.
2. `src/pages/<page>.astro` is `<Page lang="en" />`; `src/pages/es/<page>.astro` is
   `<Page lang="es" />`. Nothing else.
3. Dynamic routes (`[...id].astro`) get a twin under `src/pages/es/` whose
   `getStaticPaths` uses `getLocalizedTalks('es')` / `getLocalizedEssays('es')`.
4. Home is the reference: `src/views/Home.astro`, `src/pages/index.astro`,
   `src/pages/es/index.astro`.

## Dictionaries

One file per page/area in `src/i18n/ui/`: `common.ts` (header, footer, theme toggle,
language link), `home.ts`, and `about.ts`, `contact.ts`, `speaking.ts`, `writing.ts`,
`notFound.ts` as they are added. Two agents never edit the same file.

```ts
import { defineDict, useTranslations } from './index';
export const about = defineDict({
  en: { title: 'About' /* … */ },
  es: { title: 'Sobre mí' /* … */ },
});
export const useAbout = (lang: Lang) => useTranslations(about, lang);
// in a view:  const t = useAbout(lang);  t('title');  t('count', { n: 3 })  // "{n}" interpolation
```

`defineDict` types `es` as exactly the keys of `en`: a missing or extra key fails
`npx astro check`. Values are plain strings; markup that must differ per language is split
into keys in the view.

## Content overlays

The English collections (`src/content/talks`, `src/content/writing`) decide what exists,
what is a draft and all non-text fields. Spanish text lives in overlays matched by id (same
filename): `src/content/talks-es/` (`talksEs`) and `src/content/writing-es/` (`writingEs`).
Schemas are in `src/content.config.ts`.

`src/lib/i18nContent.ts`:

- `getLocalizedTalks(lang)` / `getLocalizedEssays(lang)` return
  `{ id, lang, entry, overlay?, data, translated }`. For `es`, `data` is the English data
  with the overlay's fields on top. Every published talk is in the Spanish list (those
  without an overlay fall back to English, `translated: false`); essays without a
  `writing-es/` file are excluded.
- `renderLocalized(item)` renders the overlay body when there is one.
- `hasSpanishTalk(id)` / `hasSpanishEssay(id)`, for `hasAlternate` on the English pages.

Draft filtering is the English one (`getPublishedTalks`, `getPublishedEssays`).

## Adding a translation

- **Page**: dictionary in `src/i18n/ui/<page>.ts`, view, two wrappers, an `es` Markdown
  twin (below). Link from the nav/footer with `localizePath`.
- **Talk**: add `src/content/talks-es/<id>.md` (frontmatter `title`/`summary`/`description`
  optional, body translated). Nothing else.
- **Essay**: add `src/content/writing-es/<id>.md` (`title`, `summary` required). The English
  essay page then passes `hasAlternate` from `hasSpanishEssay(id)`.

## Spanish style

Natural Spanish from Spain, tú form. Keep the English terms Spanish tech people actually use
(web, script, dev, firewall, backdoor, plugin, checklist, spider, playbook, skimmer…); never
force a rare Spanish equivalent. Talk titles and named concepts stay as they are.

## AI layer

- Twin path rule: `/es/` -> `/es/index.md`, `/es/about/` -> `/es/about.md`
  (`src/lib/ai/paths.ts`).
- Builders take `lang` and pass it to `makePage` (`homePage(lang)` in
  `src/lib/ai/pages/home.ts`). Page and twin read the same dictionary, so the copy cannot
  drift. Add `src/pages/es/<page>.md.ts` and append the `('es')` builder to
  `buildMarkdownPages()` in `src/lib/ai/registry.ts`.
- `llms.txt` lists English pages as before and gets one extra `## Español` section with every
  registry page under `/es/` (filter: `getMarkdownPagesByLang('es')`, by route, not by the
  talk's spoken language). New Spanish twins appear there automatically. `llms-full.txt`
  includes them at the end.
- Until every `/es/` page exists, `check:ai` reports the links from `/es/index.md` and
  `llms-full.txt` to missing Spanish pages.
