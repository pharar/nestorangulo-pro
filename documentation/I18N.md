# Internationalisation (en / es)

The site is English-first with a Spanish version. English keeps its URLs (`/about/`);
Spanish lives under `/es/` with the same path segments (`/es/about/`,
`/es/speaking/<id>/`, `/es/writing/<id>/`). There is no automatic redirect by browser
language: the visitor chooses with the language link in the header.

## How locales and routes work

- `astro.config.mjs` declares `i18n` (`defaultLocale: 'en'`, `locales: ['en', 'es']`,
  `prefixDefaultLocale: false`) and the sitemap `serialize` hook (alternates `en` / `es`, only for pages that exist in both languages, see "Link localisation and the sitemap").
  `src/i18n/config.ts` mirrors it for code (`LANGS`, `Lang`, `DEFAULT_LANG`, `OG_LOCALES`).
- The language of a request comes from the URL: `langFromUrl(Astro.url)`.
  `BaseLayout` does this itself, so a page only passes `lang` when its _content_ language
  differs from the route (a Spanish-language talk on the English route).
- `src/i18n/utils.ts`: `langFromUrl`, `stripLang`, `localizePath(path, lang)`,
  `alternatePath(path)`, `switchTarget(pathname, hasAlternate)`, `formatDate(date, lang)`.
  Always build internal links with `localizePath('/about/', lang)`.
- `BaseLayout` takes `hasAlternate` (default `true`). While true it emits
  `hreflang` `en` / `es` / `x-default` (English), `og:locale:alternate`, and the language
  link points at the equivalent page. Pass `hasAlternate={false}` for a page that exists in
  one language only (an essay without a translation, the 404): no hreflang, and the
  language link goes to the other language's section index (`/writing/`, `/speaking/`) or home.
- Canonical, `<html lang>`, `og:locale` and JSON-LD `inLanguage` are per page; the
  breadcrumb root is "Home" / "Inicio".
- The header language link (`LanguageSwitch.astro`) is a plain `<a>` showing the _target_
  code ("ES" on English pages, "EN" on Spanish ones), with `hreflang`, `lang` on the text
  and an aria-label in the target language. No JavaScript, no flags.

## The page pattern: view + thin wrappers

1. Put the markup in `src/views/<Page>.astro`, taking `lang: Lang`. All copy comes from a
   dictionary; links go through `localizePath`.
2. `src/pages/<page>.astro` is `<Page lang="en" />`; `src/pages/es/<page>.astro` is
   `<Page lang="es" />`. Nothing else.
3. Dynamic routes (`[...id].astro`) get a twin under `src/pages/es/` whose
   `getStaticPaths` uses `getLocalizedTalks('es')` / `getLocalizedEssays('es')`.
4. Home is the reference: `src/views/Home.astro`, `src/pages/index.astro`,
   `src/pages/es/index.astro`.

## Dictionaries

One file per page/area in `src/i18n/ui/`: `common.ts` (header, footer, theme toggle,
language link), `home.ts`, and `about.ts`, `contact.ts`, `speaking.ts`, `writing.ts`,
`notFound.ts` as they are added. Two agents never edit the same file.

```ts
import { defineDict, useTranslations } from './index';
export const about = defineDict({
  en: { title: 'About' /* … */ },
  es: { title: 'Sobre mí' /* … */ },
});
export const useAbout = (lang: Lang) => useTranslations(about, lang);
// in a view:  const t = useAbout(lang);  t('title');  t('count', { n: 3 })  // "{n}" interpolation
```

`defineDict` types `es` as exactly the keys of `en`: a missing or extra key fails
`npx astro check`. Values are plain strings; markup that must differ per language is split
into keys in the view.

## Content overlays

The English collections (`src/content/talks`, `src/content/writing`) decide what exists,
what is a draft and all non-text fields. Spanish text lives in overlays matched by id (same
filename): `src/content/talks-es/` (`talksEs`) and `src/content/writing-es/` (`writingEs`).
Schemas are in `src/content.config.ts`.

`src/lib/i18nContent.ts`:

- `getLocalizedTalks(lang)` / `getLocalizedEssays(lang)` return
  `{ id, lang, entry, overlay?, data, translated }`. For `es`, `data` is the English data
  with the overlay's fields on top. Every published talk is in the Spanish list (those
  without an overlay fall back to English, `translated: false`); essays without a
  `writing-es/` file are excluded.
- `renderLocalized(item)` renders the overlay body when there is one.
- `hasSpanishTalk(id)` / `hasSpanishEssay(id)`, for `hasAlternate` on the English pages.

Draft filtering is the English one (`getPublishedTalks`, `getPublishedEssays`).

## Adding a translation

- **Page**: dictionary in `src/i18n/ui/<page>.ts`, view, two wrappers, an `es` Markdown
  twin (below). Link from the nav/footer with `localizePath`.
- **Talk**: add `src/content/talks-es/<id>.md` (frontmatter `title`/`summary`/`description`
  optional, body translated). Nothing else.
- **Essay**: add `src/content/writing-es/<id>.md` (`title`, `summary` required). The English
  essay page then passes `hasAlternate` from `hasSpanishEssay(id)`.

## Link localisation and the sitemap

Authors write internal links the same way in both languages (`/speaking/<id>/`,
`/writing/<id>/`, `/about/`, ...). Never hand-write `/es/`.

- `src/lib/i18nLinks.mjs` knows, from the content folders alone (node `fs`, cached once
  per build, no dependency on build output), which English routes also exist in Spanish:
  the pages in `src/pages/es/*.astro`, every non-draft talk with a `talks-es/` overlay, and
  every non-draft essay with a `writing-es/` file.
- `src/lib/hastLinksEs.mjs` (Sätteri hast plugin, registered next to the footnotes plugin,
  Spanish content folders only) rewrites each root-relative `href` to `/es/...` when the
  Spanish page exists; otherwise the English URL stays. Skipped: `/_astro/`, `/og/`, files
  with an extension, `#` anchors, external URLs, hrefs already under `/es/`. Fragments and
  query strings are kept.
- The Markdown twins of Spanish entries get the same rewrite: `authored(body, 'es')` in
  `src/lib/ai/markdown.ts`, called by `talkPage` / `writingPostPage` when the body is an overlay's.
- The sitemap `serialize` in `astro.config.mjs` adds `en` / `es` alternates only for pages
  with a Spanish counterpart (same codes as the HTML `<link>`s). An untranslated essay is
  listed once, without alternates; no `/es/` URL exists for it.

## Spanish style

The `i18n` project skill (`.claude/skills/i18n/SKILL.md`) is the checklist for adding a
talk, essay, page or string. Natural Spanish from Spain, tú form. Keep the English terms Spanish tech people actually use
(web, script, dev, firewall, backdoor, plugin, checklist, spider, playbook, skimmer…); never
force a rare Spanish equivalent. Talk titles and named concepts stay as they are.

## Pages covered

Every page exists in both languages: home, `/about/`, `/contact/`, `/speaking/` and every
talk, `/writing/` and the essays that have a `writing-es/` file (today: one). The only
pages without a counterpart are the untranslated essays (no hreflang; the language link
goes to `/writing/` in the other language) and the 404s.

## The Spanish 404

`src/pages/es/404.astro` (the `NotFound` view with `lang="es"`) builds to
`dist/es/404/index.html`. Cloudflare Pages serves `404.html` files, so the inline
`spanish-404` integration in `astro.config.mjs` (`astro:build:done`) moves it to
`dist/es/404.html` and removes `dist/es/404/`; Pages then uses it for unmatched paths under
`/es/`. It is never a URL of its own: the sitemap `filter` drops `/404/` paths, it has no
canonical, no hreflang and no Markdown twin (`NO_MARKDOWN` in `src/lib/ai/paths.ts` lists
`/404` and `/es/404`; `check:ai` skips both). If the 404 stops being served, check that
hook first.

## Footnotes in Spanish content

The Markdown renderer (Astro 7's default, Sätteri) emits English accessibility text for
footnotes: an sr-only `<h2 id="footnote-label">Footnotes</h2>` and
`aria-label="Back to reference N"` on each back-link. `src/lib/hastFootnotesEs.mjs` is a hast
plugin, registered in `astro.config.mjs` through `markdown.processor: satteri({ hastPlugins })`
(needs `@astrojs/markdown-satteri`, a dev dependency). Its factory runs only for files under
`src/content/*-es/`, rewriting them to "Notas" / "Volver a la referencia N"; English files
are never touched, so their HTML is unchanged. The visible heading is a CSS `::before`, which
`global.css` switches to "Notas" under `:root[lang='es']`. Do not use `markdown.rehypePlugins`:
it needs the unified processor, which is not installed.

## Structured data

`personNode(locale)` keeps every fact and the `@id` (`https://nestorangulo.pro/#person`) and
only localises the free-text `description` (from the `home` dictionary); `jobTitle` is "Head
of Security" in both languages. The `WebSite` node is left in English (`inLanguage: en`, one
site-level entity). On essays, `workTranslation` / `translationOfWork` and `mentions` are
declared inline with their language's URL, so every `@id` resolves inside the page's graph.

## `npm run check:i18n`

`scripts/check-i18n.mjs` reads `dist/` (or a directory passed as the first argument) and
runs in CI after `check:ai`. It fails when:

- a page's `lang-switch` link or `hreflang` alternate points at a page that was not built;
- a page with hreflang lacks its counterpart, its hreflang set is not exactly
  `en` / `es` / `x-default` (English), the switch is not the other language's page, or a
  page with a counterpart declares no hreflang;
- a Spanish page links to an English route that has a Spanish counterpart (a missed rewrite),
  or to a page that was not built (assets, `.md`, `.pdf`, the language switch and links to
  English pages with no Spanish version excepted);
- a short list of English UI words ("Back to", "Speaking", "Writing", "Skip to content",
  "Themes", "Footnotes", ...) shows in Spanish visible text outside `lang="en"` elements
  (a heuristic: extend `ENGLISH_UI` when a new UI string appears);
- the sitemap lists a 404, omits a built page, gives a page `en` / `es` alternates when only
  one language exists, or lacks them when both do.

Talk titles and summaries of English-language talks stay English on the Spanish pages on
purpose (the overlay only translates what it contains); they sit in text the checker cannot
tell from UI, so they are not scanned for English prose.

## AI layer

- Twin path rule: `/es/` -> `/es/index.md`, `/es/about/` -> `/es/about.md`
  (`src/lib/ai/paths.ts`).
- Builders take `lang` and pass it to `makePage` (`homePage(lang)` in
  `src/lib/ai/pages/home.ts`). Page and twin read the same dictionary, so the copy cannot
  drift. Add `src/pages/es/<page>.md.ts` and append the `('es')` builder to
  `buildMarkdownPages()` in `src/lib/ai/registry.ts`.
- `llms.txt` lists English pages as before and gets one extra `## Español` section with every
  registry page under `/es/` (filter: `getMarkdownPagesByLang('es')`, by route, not by the
  talk's spoken language). New Spanish twins appear there automatically. `llms-full.txt`
  includes them at the end.
- All Spanish twins are registered in this order, mirroring the English one: home, about,
  speaking, writing, contact, talks (newest first), essays. `llms.txt` therefore lists them
  in that order under `## Español`.
