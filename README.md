# nestorangulo.pro

Personal authority site for Nestor Angulo de Ugarte — Head of Security, CISSP, security program builder.

Built with [Astro 7](https://astro.build), deployed on [Cloudflare Pages](https://developers.cloudflare.com/pages/).

## Requirements

- Node 26 LTS ("Lithium") — `nvm use` will read `.nvmrc`
- npm ≥ 10 (the repo pins `npm@12.2.2` via `packageManager`)

## Local development

```bash
nvm use
npm install
npm run dev        # http://localhost:4321
```

`npm install` also runs the `prepare` script, which points `core.hooksPath` at `.githooks/`.
Its `pre-commit` hook formats staged files with Prettier, so the CI Format check never
fails on whitespace. Skip it for one commit with `git commit --no-verify`.

Before opening a PR, reproduce what CI will check:

```bash
npm run format:check && npm run check
npm run build && npm run check:ai && npm run check:urls && npm run check:csp
```

## Available scripts

| Script                  | Description                                                        |
| ----------------------- | ------------------------------------------------------------------ |
| `npm run dev`           | Start dev server                                                   |
| `npm run build`         | Build static output to `./dist`                                    |
| `npm run preview`       | Preview the production build                                       |
| `npm run check`         | Astro + TypeScript type checking                                   |
| `npm run check:urls`    | URL contract of the built site (canonicals, sitemap, links)        |
| `npm run check:csp`     | CSP contract of the built site (inline scripts/styles vs policy)   |
| `npm run check:ai`      | AI-readable layer of the built site (llms.txt, twins, JSON-LD)     |
| `npm run check:content` | Content contract of the Markdown sources (no build needed)         |
| `npm run test:scripts`  | Unit tests for the scripts (`node --test`)                         |
| `npm run gate`          | Every local check in one go — run before handing work over         |
| `npm run format`        | Format all files with Prettier                                     |
| `npm run format:check`  | Check formatting                                                   |
| `npm run og`            | Regenerate `public/og-default.png` from `assets/og/og-default.svg` |
| `npm run post`          | Write and publish an essay (documentation/WRITING.md)              |
| `npm run housekeeping`  | Report what has fallen behind — see [Housekeeping](#housekeeping)  |
| `npm run talk`          | Talk cards and slide decks — the `talk` skill drives it            |

Favicons are generated by `node scripts/build-favicon.mjs` (no npm alias). Both asset
scripts write into `public/` and their output is **committed** — the deploy does not run
them.

## Content

Talks are an Astro Content Collection loaded from `src/content/talks/*.md` and validated
against the schema in `src/content.config.ts`. Each entry requires `title`, `event`,
`date`, `format`, and `themes` (from a fixed enum); `draft: true` keeps an entry out of
the build. Adding a talk means adding a Markdown file — no code change.

`/speaking` lists them; `/speaking/[...id]` renders each one. The conventions (slug, the
two slides links, the featured shelf, language) are in
[documentation/SPEAKING.md](./documentation/SPEAKING.md), slide hosting in
[documentation/SLIDES-R2.md](./documentation/SLIDES-R2.md); `npm run talk -- <verb>` does
the mechanics and the `talk` skill the procedure.

Essays work the same way: `src/content/writing/*.md`, `draft: true` to hold one back.
`/writing` lists them, `/writing/[...id]` renders each, `/rss.xml` carries them. The
schema, the social card and the feed are explained in
[documentation/WRITING.md](./documentation/WRITING.md); `npm run post` does the mechanics
and the `post` skill the procedure.

Every published talk and essay automatically gets a Markdown twin (`/speaking/<id>.md`,
`/writing/<slug>.md`), an entry in `/llms.txt` and `/llms-full.txt`, and its JSON-LD node
(`Event` / `BlogPosting`). Copy that lives only in `.astro` templates (home, about, contact,
speaking intro) is duplicated in `src/lib/ai/pages/*` and must be updated by hand. In Claude
Code, the `ai-readable-layer` skill lists what to touch for each kind of change.

## Security & SEO

- **Content Security Policy** — declared in `astro.config.mjs` under `security.csp`
  (Astro 7), `'self'`-only. Adding a third-party script, font, or embed requires editing
  that policy.
- **Security headers** — HSTS (preload), `X-Frame-Options: DENY`, `nosniff`,
  `Referrer-Policy`, and a restrictive `Permissions-Policy`, all via `public/_headers`.
- **Sitemap** — generated by `@astrojs/sitemap` at `/sitemap-index.xml`.
- **AI-readable layer** — `/llms.txt`, `/llms-full.txt`, a Markdown twin of every page
  (`/about/` → `/about.md`, linked via `rel="alternate"`) and a JSON-LD `@graph`, checked
  by `npm run check:ai`. See [documentation/AI-READABLE.md](./documentation/AI-READABLE.md).
- **Canonical URLs** — `trailingSlash: 'always'`. `/about/` is the real URL; `/about`
  308-redirects to it. Canonicals come from `Astro.url.href` (never hardcode the prop),
  and internal links carry the slash so they resolve in one hop. See
  [documentation/DEPLOY.md](./documentation/DEPLOY.md#trailing-slashes-are-the-canonical-url-form).
- **Redirects** — renamed routes keep 301s in `public/_redirects`.
- **Vulnerability reporting** — see [SECURITY.md](./SECURITY.md) and
  `/.well-known/security.txt`.

## Workflow

**Work on a branch, merge to `main` through a pull request.** `main` is what Cloudflare
deploys to production, so anything that lands there is live within a minute or two — the
PR is the only place a problem can be caught before visitors see it.

```bash
git switch -c fix/some-thing     # or feat/… , chore/… , content/…
# …work, commit…
git push -u origin fix/some-thing
# open a PR against main, let CI go green, then merge
```

Pushing straight to `main` is what this workflow replaces: it skipped the Lighthouse
audit entirely (see below) and published unreviewed changes directly to production.

## CI

Every PR against `main`, and every push to `main`, runs `.github/workflows/ci.yml`:

1. **Format check** — `npm run format:check`. Independent of the other jobs, so a
   formatting slip never hides a real failure behind a skipped build.
2. **Type check** — `astro check` with TypeScript strict
3. **Build** — `astro build`, then `npm run check:ai` (llms.txt, Markdown twins, JSON-LD
   graph, robots.txt; see [AI-READABLE.md](./documentation/AI-READABLE.md)), uploading
   `dist/` as an artifact

Independently of those, a **Content** job runs `npm run check:content` and
`npm run test:scripts`: the content contract (what the Zod schema cannot see) and the
script tests. It needs no build. Locally, `npm run gate` runs all of the above in one go.

Then, in parallel off the build artifact:

4. **URL contract** — `npm run check:urls`. Asserts canonicals, sitemap and internal
   links all agree on the trailing-slash form. Added because that invariant broke
   silently: the build succeeded and Lighthouse passed while 37 of 41 canonicals
   pointed at a redirect.
5. **Link check** — [lychee](https://lychee.cli.rs) over the built HTML, the markdown,
   and `security.txt`. Added because the `security.txt` Policy URL was dead for months.
   Config in `lychee.toml`; the site's own domain is excluded there, deliberately.
6. **Lighthouse audit** — asserts a11y ≥ 0.95, SEO ≥ 0.95, perf ≥ 0.9, and warns under
   best-practices 0.9

`npm run check:csp` is **not** a CI step yet: it runs locally and as part of
`npm run housekeeping:verify`.

CodeQL also runs on every PR. It is GitHub's _default setup_, configured in the repo
settings rather than in `.github/workflows/`, which is why no file here describes it.

Dependency and action updates arrive as PRs via `.github/dependabot.yml` (weekly, npm
and github-actions). What Dependabot cannot see — the Node and npm pins, stale overrides,
held majors — is covered by [housekeeping](#housekeeping).

> **Previously the Lighthouse job was gated to `pull_request` only.** Since all work
> landed as direct pushes to `main`, it was skipped on every single run — the audit had
> effectively never gated anything. It now runs on both events.

CI does **not** deploy, and Cloudflare will publish a broken build regardless of whether
CI passed. What makes CI a real gate is branch protection: with it enabled, a red run
blocks the _merge_, and nothing reaches `main` — and therefore production — until the
checks are green.

<details>
<summary>Enabling branch protection on <code>main</code></summary>

Settings → Rules → Rulesets → New ruleset, targeting `main`:

- **Require a pull request before merging**, with **Required approvals set to 0** —
  GitHub will not let you approve your own PR, so requiring 1 on a single-maintainer
  repo locks you out of your own `main`.
- **Require status checks to pass before merging**, selecting:
  - `Format check`
  - `Content` — a new check: GitHub only offers it in this list after it has run once, and
    it is **not required until you add it here by hand**
  - `Type check`
  - `Build` (includes `check:ai`)
  - `URL contract`
  - `Link check`
  - `Lighthouse audit`
  - `CodeQL`

Do **not** require the `Cloudflare Pages` check: it reports the preview deploy, which
duplicates `Build`, and a third-party check that stalls is a merge you cannot complete.

Leave "Do not allow bypassing" off if you want an escape hatch for urgent fixes.

</details>

## Housekeeping

```bash
npm run housekeeping:baseline            # snapshot the built site before changing anything
npm run housekeeping                     # what is behind: runtime, deps, overrides, advisories, actions
npm run housekeeping:verify -- --assets  # the full local gate, plus a diff against the snapshot
```

The procedure, the rule for what "latest" means for each piece, what is deliberately held
back (TypeScript 7) and why, and the log of past runs are in
[documentation/HOUSEKEEPING.md](./documentation/HOUSEKEEPING.md). In Claude Code the
`housekeeping` skill runs the same procedure.

## Deployment

Cloudflare Pages builds straight from GitHub: pushes to `main` go to production, PRs get
preview URLs. See [documentation/DEPLOY.md](./documentation/DEPLOY.md) for build
settings, the `NODE_VERSION` pin, the platform-interpreted files in `public/`, post-deploy
verification, and rollback.
